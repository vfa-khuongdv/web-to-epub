# AGENTS.md

Local-first tool that crawls rendered pages of web novel sites and exports Kindle EPUBs. One Express process serves both `/api` and the built React frontend; the story library lives in local SQLite.

## Commands (from repo root)

- `npm install` — installs backend + `frontend/` (npm workspaces). Add `npx playwright install chromium` to actually crawl/render.
- `npm test` — vitest, all tests in ~2s; tests are hermetic (network and Chromium mocked), no setup needed.
- `npm run test:e2e` — Playwright E2E against the built app (`npm run build` runs first; needs `npx playwright install chromium`). Serial, uses a throwaway library in `e2e/.data/` and a local fixture site. Specs are `e2e/tests/*.e2e.ts` (not `*.test.ts`, so vitest keeps ignoring them); typecheck with `npx tsc -p e2e --noEmit`. Add-by-URL/TOC and watch-check happy paths need a real allowlisted site, so they stay unit-tested. CI (`.github/workflows/ci.yml`) runs `npm test`, both typechecks and this suite on pushes and PRs.
- `npx vitest run src/services/crawl.test.ts -t "test name"` — single file / single test.
- `npm run build` — `tsc` → `dist/` then `vite build` → `public/`. Required before `npm start` (it only runs `dist/server.js`); `make start` builds first.
- `npm run dev` (backend watch: `tsc --watch` + nodemon) and `npm run dev:frontend` (Vite dev server proxies `/api` → `localhost:3100`).
- `npx tsc -p frontend --noEmit` — frontend typecheck; `vite build` does NOT typecheck frontend.
- `npm run app:win` / `npm run app:linux` — NSIS `.exe` + zip / AppImage + deb, x64. Build them on the target OS only (sharp, Electron and the bundled Chromium are per-platform); `.github/workflows/desktop.yml` does that on a `v*` tag or manually. Narration on Windows/Linux is wired (`uv.exe` zip, `venv\Scripts\python.exe`) but untested there — `tts/constraints.txt` was frozen on macOS and may need a per-platform set, and the in-app self-update works per OS (`updateKind` in `services/appInstaller.ts`; the preload asks `update:can-install` and hides the bridge when it is null): macOS swaps the `.app` from the `-arm64-mac.zip`, Windows runs the NSIS `Setup.*.exe` silently (`/S --updated --force-run`, only if an `Uninstall *.exe` sits next to the exe — the portable zip just links to the release), Linux swaps the running AppImage (`$APPIMAGE`) and restarts it; a `.deb` only links to the release. `pickUpdateAsset` picks the asset by platform. Only the macOS path has been run for real. Unsigned: Windows shows SmartScreen.
- No lint/format tooling in this repo. `make help` lists Docker/packaging targets (`docker-build`, `docker-push`, `app`, `release-mac`).

## Architecture

- Entry: `src/server.ts` (Express, serves `public/` + `/api`).
- Crawl pipeline: `services/renderer.ts` (Playwright + auto-scroll) → `services/extractor.ts` (Readability + custom chrome filter) → typed `ContentBlock[]` → `services/storyStore.ts` (SQLite) → `services/epubBuilder.ts` (epub-gen).
- EPUB import: `POST /api/stories/import-epub` (raw body, ≤ 100 MB, `?overwrite=1`) hashes the file into the story URL `epub:<sha1>`, parses it with `services/epubImport.ts` (streaming unzip with expanded-size caps, DRM rejected unless it is font obfuscation, DOM sanitized before `walkToBlocks`) and saves every image on disk via `services/epubMedia.ts` (`epub-media/<storyId>/<sha1-12>.<ext>`). Blocks store that relative marker; `routes/chapters.ts` maps it to `/api/stories/:id/media/:name` (+ `?vault=`) on the way out and restores it on save, and the export maps it to `file://` with the story's media dir in `localMediaRoots` — `embedImages` only reads `file://` inside those roots. Imported stories are `site: "epub"`, `watching: false`, all chapters `done`; there is no TOC, so crawl/watch controls are hidden and the crawl/watch routes refuse them.
- PDF import goes through the same route: a body starting with `%PDF-` is parsed by `services/pdfImport.ts` (`unpdf`, pdf.js without a canvas) into the same `ImportedBook` and stored as story URL `pdf:<sha1>` with `site: "epub"` (the UI labels it by the URL prefix). Chapters come from the outline, else from `Chương N`/`Chapter N` lines, else 20-page chunks; paragraphs are rebuilt from line gaps, indents and short lines ending a sentence. A page with no text layer (a scan) keeps its images, re-encoded as JPEG through `sharp`. The first image on page 1 (text layer or not) becomes the book's cover. A password-protected PDF or one whose permissions forbid copying is refused (same rule as DRM). No OCR.
- Internet Archive import: `POST /api/stories/import-archive` takes an `archive.org/details/<id>` URL and saves it as an imported book (`site: "epub"`, story URL `archive:<id>`), so the crawl/watch guards and the EPUB export apply unchanged. `services/archiveImport.ts` reads `https://archive.org/metadata/<id>` and refuses `access-restricted-item` items unless a saved archive.org session exists (Settings → Site sessions): with one, `services/archiveBorrow.ts` starts or reuses a browse/borrow through `/services/loans/loan` and captures the page images the BookReader itself shows (`request_page` grant + `BookReaderPreview.php`) — still never decrypted, never a private file, no OCR, so the book lands as image chapters (Narration reads nothing). Without a session the import fails with the "sign in" message; otherwise it imports the first public source: EPUB (`parseEpub`) → OCR text `_djvu.txt` (`textToBook` page/chapter heuristics) → PDF (`parsePdf`). archive.org is deliberately NOT in `SUPPORTED_SITES` (it is import-only, not an auto-loaded chapter list): the add box branches on the URL itself and the route validates the host.
- DTV Ebook import: `POST /api/stories/import-dtvebook` takes a `dtv-ebook.com.vn/<slug>_<id>.html` URL and saves it as an imported book (`site: "epub"`, story URL `dtv:<id>`). This site has **no chapter pages at all** — every book is a single EPUB the site hosts, so a TOC adapter/chapter fetcher cannot work on it. `services/dtvEbookImport.ts` goes through the site's own "Đọc online" link instead: `doconline.php?hash=<base64(id)>` is an epub.js shell that ships no text and names the book file in `ePubReader("images/…epub")`; that file is fetched from the same host (plain GET, no session, no Cloudflare challenge) and read with `parseEpub`, so chapters, cover and images are the book's own. A book the site hosts no EPUB for answers with an empty path (only MOBI/CBZ/PDF downloads) → `DtvEbookNoEpubError`; there is deliberately no Google Drive fallback. Like archive.org it is import-only and NOT in `SUPPORTED_SITES`; `frontend/src/lib/dtvEbookUrl.ts` routes the add box, and all three import routes share `saveImportedBook` in `routes/stories.ts`.
- Reader/preview: `frontend/src/components/ReaderOverlay.tsx` renders a chapter in a sandboxed iframe (no `allow-scripts`, chapter HTML is crawled) using the export's own `KINDLE_CSS`, so what is on screen is what the EPUB will contain. Highlights live in the `highlights` table and anchor by character offsets into the chapter's plain text (`frontend/src/lib/highlightDom.ts`); reading position and reader preferences are per-browser in `localStorage`.
- UI language: everything user-facing goes through `t()` — `frontend/src/i18n/` on the client (one file per language under `i18n/locales/`, registered in `i18n/locales/index.ts`) and `src/services/lang.ts` on the server (Vietnamese wording only, English keys). Keys are the English source text, so a missing entry renders English; `i18n/locales.test.ts` keeps every language's key set and placeholders aligned with `en.ts`, so adding a language is a new locale file plus one registry entry.
- Each site is one folder, `src/sites/<id>/` (`toc.ts` chapter list, `chapter.ts` direct fetcher, tests, `__fixtures__/`, and an `index.ts` manifest: allowlist rows, adapter, fetcher, saved-session slug), listed once in `src/sites/index.ts`; the allowlist, `getTocAdapter`, `getChapterFetcher` and the session slugs are all derived from that list (how to add one: `src/sites/README.md`). Shared plumbing stays in `services/toc/` (`http.ts`, `normalizeUrl.ts`, `types.ts`) and `services/chapters/types.ts`. A site-specific browser step (Asianfanfics' age gate) is passed to `renderPageHtml` as `afterOpen`, the renderer knows no site. `services/crawl.ts` dispatches by URL: site fetcher if present, else renderer+extractor; retries 3 times.
- Saved site sessions: `services/siteSession.ts` loads a Playwright `storageState` per hostname from `DATA_DIR/sessions/<host>.json` and `renderer.ts` injects it into every context for that host, together with the user agent recorded in the file — Cloudflare binds its cookies to the UA, so `src/config/browser.json` (shared default) and the session's UA must be what the user's browser used. Files are written by `POST /api/site-sessions/:site` (`src/routes/siteSessions.ts`, a slug allowlist: `asianfanfics` → asianfanfics.com, `truyenfull` → truyenfull.live, `archive` → archive.org), which parses a cURL copy of a request from the user's own browser; the UI copy per site lives in `frontend/src/lib/siteSessions.ts` and the dialog is `SiteSessionDialog` (opened when adding a story from a site that needs one, and from Settings → Site sessions, which also removes it). Asianfanfics uses it for a login (rated-M / subscribers-only stories, token lives about an hour); `siteSessionStatus` reports `expiresAt` from the `exp` claim of its JWT cookies, which the settings page and add flow use to warn before a crawl fails. truyenfull.live uses it for the Cloudflare check on story/chapter pages (there is no login): `sessionRequestHeaders` sends the clearance cookie + UA on the plain-fetch fast path of its TOC adapter and chapter fetcher, and both fall back to `renderPageHtml` when the request is challenged; `services/cloudflare.ts` recognizes the interstitial and phrases the "import a session" error. Its clearance lasts about half an hour, so long crawls may need a fresh import; the settings row shows `savedAt` only because `cf_clearance` carries no readable expiry. The app never stores passwords and never solves a bot check.
- Story crawls run server-side after a `202` response; progress goes over SSE (`/api/stories/live` shared channel tagged `storyId`, `/api/stories/:id/live`). `runningCrawls` and SSE subscriber maps are in-memory in `src/routes/library.ts` (one per library) — single process only.
- App settings (launch check for new chapters, defaults for a newly added book) live in a `settings` table in the normal library's `stories.db` via `services/settingsStore.ts` — one set for the whole install, *not* per library, reached over `GET/PATCH /api/settings`. The page is `frontend/src/components/SettingsOverlay.tsx` (gear in the header); theme and interface language stay in `localStorage` and are only surfaced there.
- Narration (text-to-speech, Vietnamese stories only): the app installs and runs [VieNeu-TTS](https://huggingface.co/pnnbao-ump/VieNeu-TTS) itself. `services/tts/runtime.ts` downloads a pinned standalone `uv` into `DATA_DIR/tts/bin`, lets it fetch CPython into `DATA_DIR/tts/python`, installs `vieneu==VIENEU_VERSION` (`src/config/tts.ts`) into `DATA_DIR/tts/venv` and keeps models in `DATA_DIR/tts/hf` (HF_HOME) — Settings → Narration installs/uninstalls it. One long-lived Python child (`tts/vieneu_worker.py`, JSON lines over stdin/stdout, closed after 10 min idle and on quit) serves one request at a time through `workerClient.ts`. Jobs (`routes/narration.ts`, `services/tts/narrate.ts`) narrate chapter by chapter into `<library dataDir>/audio/<storyId>/<order>.mp3` with a `<order>.json` meta (text read, variant, voice, engine version, part timings); a chapter's audio is kept when the chapter is edited or the voice changes, a restarted job skips what is done, and the per-chapter "Regenerate audio" button re-narrates one chapter (`regenerate: true`, written to `<order>.new.mp3` and swapped in, so a failed run keeps the old file). Custom voices (`services/tts/customVoices.ts`): an uploaded reference clip in `DATA_DIR/voices/` (outside `tts/`, so uninstalling keeps it), id `custom:<uuid>`; the worker enrolls it with VieNeu's `add_voice` on first synth (first 30 s only), so it works with either model. Narration has its own SSE channel `/api/narration/live`: the crawl channel's listeners treat every event as crawl progress. Playback: one app-wide player (`frontend/src/hooks/narrationPlayer.tsx`, provider inside `App`, so switching library stops it) plays a story's narrated chapters in order and keeps playing while browsing; its bar sits in the `.app` grid's bottom row, and the reader shows the same player. A story page feeds it its queue only once its narration state has loaded — an empty list would stop the chapter playing. Exports: per-chapter MP3, a streamed ZIP (`routes/audioExports.ts`, kept on disk, not in RAM), `includeNarration` on the EPUB export, and "Export audio + music": once every chapter has audio, `POST /api/stories/:id/export-audio-mix` joins them into one MP3 with the player's background music looped under it (track + volume over voice volume, sent by the page), as a job polled at `/api/exports/audio-mix/:jobId` (minutes on a long story — longer than a request may stay open). With the player's music on, the zip goes through the same job (`format: "zip"`, each chapter mixed on its own) and a chapter's download link (`?download=1&music=<id>&musicVolume=`) is mixed on the spot; the player itself always streams the plain file. Chapter files are named `<story> - 001 - <chapter>.mp3`. The join is `tts/mix_story.py`, run with an installed engine's venv Python (`runtime.python()`; numpy/soundfile/soxr are in both), one chapter in memory at a time; tests use `__fixtures__/fakeMixer.js`.
- Second narration engine, [OmniVoice](https://huggingface.co/k2-fsa/OmniVoice) (`ttsVariant: "omnivoice"`; `turbo`/`nano` are VieNeu): a separate install under `DATA_DIR/tts-omnivoice` (own uv, Python, venv, HF cache — torch, which VieNeu's onnxruntime set must not share), created by the same `createTtsRuntime` with other deps; `ttsRuntimes`/`runtimeFor`/`ttsEngines` in `runtime.ts` pick the engine by variant, and `ttsEngines.withModel` closes the other engine's idle worker first (both models do not fit in 8 GB). Offered only on a GPU (`omnivoiceUvDownloadUrl`): Apple Silicon (MPS) or an NVIDIA card on Windows/Linux x64 (CUDA, detected with `nvidia-smi`); CPU is ~17× real time. Off macOS the install first puts torch/torchaudio `+cu126` from PyTorch's index (PyPI's Windows wheel is CPU-only, and uv does not match `==2.8.0` to `2.8.0+cu126`), then installs the rest with a copy of the constraints minus torch (`runtime.ts` `torchIndex`); the CUDA path is resolved with `uv pip compile` but never run on real hardware. Worker `tts/omnivoice_worker.py`, same protocol, model revision pinned in the script. It has no preset voices — without a reference clip every part gets a new random voice — so it reads only with a clip: a custom voice or a built-in one (`builtin:<id>`, a clip listed in `tts/voices/omnivoice.json`); `synthVoice(voice, "omnivoice")` refuses the rest. Cloning uses the clip's `transcript` when there is one, else Whisper transcribes it once — a clip longer than `MAX_REF_SECONDS` is first cut at its last pause (`last_pause`), because a clip cut mid-word makes OmniVoice repeat that syllable at the end of every sentence; the prompt is saved as `<clip>.omnivoice-v2.pt` next to a custom clip (the suffix is `PROMPT_SUFFIX`, bumped when prompts are made differently), and under `DATA_DIR/voices/cache/builtin/` for a built-in one (`refPrompt` — the bundle is read-only). Model weights are CC BY-NC. Measured on an 8 GB M2: RTF ≈ 3.5 at 32 steps; fewer steps are not reliably faster there (memory-bound).
- Trust boundary is the allowlist (`SUPPORTED_SITES`, the `supported` rows of the site manifests in `src/sites/`, re-exported by `src/config/supportedSites.ts`), enforced server-side (frontend reads it from `/api/supported-sites`). New crawl domains go in a site manifest; optionally add a TOC adapter. `IMPORT_SOURCES` (the `imports` rows) lists the book-file sources (archive.org, dtv-ebook.com.vn) and is served alongside with `mode: "crawl" | "import"`; the add box's popover, its hint line and the "not a supported site" message all show the two groups apart, so a source added to either list is discoverable without touching the UI. The two lists must stay disjoint: `findSupportedSite` (and so `POST /stories`) trusts `SUPPORTED_SITES` only, and a book source put in there would be accepted for a crawl it cannot do.
- `DATA_DIR` (default `./data`) holds `stories.db` + `covers/`; nothing under `data/` is committed. The Electron app points `DATA_DIR` at userData.
- Private mode ("ẩn danh", Cmd/Ctrl+Shift+N — also +K, because Chrome keeps +N): a second library under `DATA_DIR/private/` (own `stories.db`, `covers/`, `lock.json`) behind a 6-digit code. `services/vault.ts` hashes the code with scrypt and hands out an in-memory session token; every route picks its `Library` via `libraryFor(req, res)` (token in `X-Vault-Token`, or `?vault=` for the SSE channel and cover `<img>`), so crawl state and live channels are per library too. Frontend: `frontend/src/vault/` (`index.tsx` + `token.ts`); switching modes remounts `<App>` from `main.tsx`.
- Frontend is React 18 + Vite + Tailwind 4 and builds into `../public`; never hand-edit `public/` or `dist/`.

## Gotchas

- Requires Node ≥ 22.5: SQLite is `node:sqlite` `DatabaseSync` (no better-sqlite3), experimental warning is expected in test output.
- `epubBuilder.ts` downloads chapter images itself and derives extensions from magic bytes, because epub-gen guesses `mime.getType(url)` and breaks on extension-less CDN URLs. Don't hand image URLs back to epub-gen.
- `epubBuilder.ts` also embeds `<audio>`/`<video>`: epub-gen ignores them and strips `controls`, so the finished `.epub` is unzipped and patched (media files + manifest items + `controls` restored) via `packMedia`. That patch assumes epub-gen's fixed layout (`OEBPS/content.opf`, chapters at `OEBPS/*.xhtml`).
- Chapter edits ARE persisted via `PATCH /api/stories/:id/chapters/:order` ("Save Chapter").
- Crawl code re-reads the story from SQLite before `updateMeta` because a user may save meta mid-crawl — keep that read-before-write pattern.
- Never bypass login/paywall/DRM (product constraint); locked chapters must fail with a clear Vietnamese error.
- Asianfanfics is Cloudflare-protected: plain fetch gets a 403 challenge page, so its TOC adapter renders through `renderPageHtml` and its chapter fetcher reads the htmx-swapped content div (`[hx-get^='/htmx/chapter/']` inside `#bodyText`, `/htmx/story/<id>/<token>` for a foreword) with `walkToBlocks` (exported from `extractor.ts`) instead of Readability. The page `<title>` can stay stale ("Just a moment...") even when real content rendered — take titles from `h1`. A subscribers-only chapter the account cannot read arrives as a `/htmx/teaser/` div holding the first paragraphs plus a notice: the fetcher reports it as locked instead of saving a truncated chapter (the "Subscribers only" header badge is on every page, so it is NOT a lock signal — treating it as one turned failed loads into permanent errors). The account's AFF login token lasts about an hour: when a saved session no longer authenticates, the guest userbar (`header[data-aff-userbar-shell] a[href="/login"]`) is the signal, and the adapter/fetcher report "session has expired" instead of the guest-level lock. Rated-M / subscribers-only content needs a fresh session (Settings → Site sessions, or the dialog shown when adding an Asianfanfics story) plus the account's "Filter mature content" setting off.
- Private mode is a lock on the app, not encryption: `data/private/stories.db` is a plain SQLite file. Don't describe it as encrypted, and don't let an invalid token fall back to the public library — `libraryFor` answers 401 and returns `null` for exactly that reason.
- `LOCKED_CONTENT_RE` in `extractor.ts` matches text on the *crawled page*, not text this app writes — the supported sites publish their anti-adblock notices in Vietnamese. Translating it silently turns the check off (it already happened once).
- `KINDLE_CSS` is exported from `epubBuilder.ts` and mirrored in `frontend/src/lib/readerPreview.ts`; they must stay identical or the reader stops being an honest preview.
- Server-side wording is module state in `services/lang.ts`, set per request from the `X-Lang` header. Fine because the app is single-process and single-reader; it would have to be per-request in a multi-user server. It defaults to English when the header is absent, which is what the tests rely on.
- Narration speed on an M2 CPU: Turbo (default, "Quality") RTF ≈ 0.75, Nano 8 steps ("Fast") ≈ 0.41 — about a day per 150-chapter story. The spike numbers and the rest of the design are in `docs/superpowers/specs/2026-09-25-chapter-tts-design.md`. Tests never start Python: `services/tts/__fixtures__/fakeWorker.js` speaks the worker protocol. Python cannot read inside `app.asar`, so `tts/**` is in `asarUnpack` and `WORKER_SCRIPT` points at `app.asar.unpacked`.
- Voice list and "Preview" never load a model: `services/tts/voiceCatalog.ts` reads `tts/voices/` (VieNeu presets per model in `presets.json`, OmniVoice's built-in clips in `omnivoice.json`, and a pre-rendered `samples/<variant>/<name>.mp3` per voice), so Settings → Narration lists and plays them before an engine is installed. A voice without a bundled sample (a custom one, a preset newer than the bundle) is rendered once and cached (next to a custom clip, else `DATA_DIR/voices/cache/samples/`). After bumping an engine or adding a built-in clip, `npm run build` then `DATA_DIR=<a data dir with both engines installed> node scripts/voice-samples.js [--force]` regenerates them.
- OmniVoice's set is `tts/omnivoice-constraints.txt` (same rule: a `uv pip freeze` of a working env, bumped together with `OMNIVOICE_VERSION`).
- VieNeu's dependencies are pinned as a whole by `tts/constraints.txt` (a `uv pip freeze` of an environment that worked), passed as `-c` at install. Pinning only `vieneu` broke Turbo: newer `huggingface_hub` stores blobs in a shared, sharded folder, and onnxruntime refuses a model whose external `.data` file resolves outside the `.onnx` file's own folder. `DATA_DIR/tts/hf/.constraints` records which pin set downloaded the cache; a mismatch wipes and re-downloads it. Regenerate the file from a working env when bumping `VIENEU_VERSION` — never edit versions by hand — and `installed.json` stores its hash, so a change makes the app ask to install again.
- `embedMedia`/`embedImages` read `file://` media only from the folders passed as `localMediaRoots` (an imported book's media dir, the story's audio dir when narrating): chapter HTML also comes from the client, and must not be able to pull arbitrary local files into a book.
- Docker runtime relies on `CHROMIUM_NO_SANDBOX=1` and expects a volume at `/app/data`. `npm run app:mac` is arm64-only, ad-hoc signed, and bundles Playwright shell Chromium via `build/ms-playwright`.

## Conventions

- Tests are colocated as `**/*.test.ts` — backend under `src/` (excluded from the tsc build), frontend under `frontend/src/`; fixtures in `__fixtures__/`.
- Frontend layout: API calls live in `frontend/src/lib/api/<domain>.ts` (`index.ts` re-exports, import from `../lib/api`); a book-hosting site the add box imports is one row in `lib/bookUrlSources.ts`, and an imported book's source label is one row in `lib/storySource.ts`. Big components keep state and handlers, the presentational pieces are their own files (`AddStoryBox`, `StoryMetaFields`, `ChapterPager`, `PendingChapterRow`, `ReaderSidebar`, `ReaderTextPanel`, `HighlightPalette`); pure logic that a component needed (`lib/libraryRows.ts`) is tested on its own.
- Style UI with **Tailwind utilities at the call site** — the `@theme` tokens in `frontend/src/styles.css` are utilities too (`bg-raised`, `text-ink-2`, `border-rule-2`, `rounded-tool`, …), so dark mode follows automatically. Do not add new component classes to `styles.css`; the ones already there are legacy and get removed only when the element using them is reworked.
- Conventional commit prefixes; messages in Vietnamese or English (`feat(chapter): ...`).
- Release process: `RELEASE.md` (version bump → tag → GitHub release → DMG → Docker Hub).
- Product intent: `PRODUCT.md`. Design tokens/typography: `frontend/DESIGN.md`. Feature specs/plans: `docs/superpowers/`.
